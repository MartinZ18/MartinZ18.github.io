AMICANA 2.0 En producción

FastAPI · MySQL · MercadoPago · n8n/Python 3.11
Instituto Cultural Argentino Norteamericano, Mendoza/2025–2026

El instituto cobraba las cuotas a mano y conciliaba los pagos uno por uno. Hoy hay un sistema con tres roles, cobro integrado con MercadoPago Checkout Pro, auditoría de cada acción que modifica datos, y un asistente que responde consultas de alumnos fundamentado en la información real del instituto.

Lo usan alumnos y personal administrativo. Eso cambia cómo escribís el código: un bug acá no lo descubre un test, lo descubre alguien que quería pagar la cuota.

Código → Workflows del RAG →
Lo técnico
  • Asistente con RAG — embeddings de 768 dimensiones en Postgres con pgvector, recuperación por similitud coseno, generación restringida al contexto recuperado. Si no sabe, deriva a secretaría en vez de inventar.
  • OCR de facturas — extracción con un modelo de visión local (Ollama) y alternativa en la nube, con validación de CUIT por Módulo 11.
  • Auth — JWT con roles, hashing con bcrypt, control de acceso por dependencia en cada endpoint protegido.
  • Verificación — suite de regresión de 28 casos con Playwright, más tests de rutas con pytest y mocks.
  • Deploy — Docker multi-stage y GitHub Actions que corre los tests antes de publicar.

Inventario EGI

FastAPI · Kubernetes · MongoDB · SQL Server/Active Directory
Inventario de equipamiento de laboratorio/2026

Un inventario de equipos que tenía que autenticar contra el directorio corporativo existente y convivir con dos motores de base de datos distintos. La parte interesante no fue la API: fue la red.

Es el proyecto donde entendí que desplegar no es docker run. Segmentar, restringir tráfico entre pods y dejar el pipeline andando sobre un runner propio es trabajo de infraestructura, no un paso final.

Código →
Lo técnico
  • Autenticación contra Active Directory por LDAP, sin usuarios propios del sistema.
  • Dos motores de datos — SQL Server para lo transaccional, MongoDB para lo documental.
  • Kubernetes con 7 NetworkPolicies de tipo zero-trust: nada habla con nada salvo que esté declarado.
  • Firewall pfSense y segmentación de red entre servicios.
  • CI/CD sobre runner self-hosted, porque el entorno no salía a internet.

Clasificador de incidentes por correo

n8n · Ollama · Gmail API · Telegram/LLM local
Automatización de triage/2026

Alguien tenía que leer la casilla de soporte y decidir qué escalaba. Ahora el flujo lee los correos, un modelo local clasifica gravedad, y solo llega una notificación a Telegram cuando efectivamente hay que mover a alguien.

Usé un modelo local a propósito: el contenido de los correos no sale de la máquina y no hay costo por token. Es el mismo criterio que aplico cuando un cliente pregunta cuánto le va a costar la automatización por mes.

Código y workflow →
Lo técnico
  • Inferencia local con Ollama — sin API de pago, sin datos saliendo de la red.
  • Salida estructurada del modelo, para que la decisión de escalar sea un campo y no una interpretación de texto libre.
  • Manejo de errores explícito — un JSON mal formado degrada el flujo, no lo tira abajo.
  • Notificación selectiva — el valor no es avisar, es no avisar cuando no hace falta.

02 — Un bug

El índice que rompía el sistema en silencio

Si tuviera que elegir una sola cosa para que mires, es esta. No por el bug — por cómo se encontró.

Síntoma: el chatbot decía que no tenía información, con la información cargada

El asistente de AMICANA contestaba «el contexto disponible no incluye información sobre modalidades ni cuotas» — con los cursos y las preguntas frecuentes efectivamente guardados en la base. El modelo se portaba perfecto: no alucinaba, decía la verdad sobre lo que le habían dado. El problema era que le estaban dando un solo documento.

La causa era un índice vectorial ivfflat creado con lists = 100 sobre una tabla de nueve filas. Ese tipo de índice agrupa los vectores en listas y, por defecto, revisa una sola. Con nueve documentos repartidos en cien grupos, la búsqueda entraba a un grupo, encontraba un documento y devolvía uno.

No tiraba error. No tiraba warning. Devolvía 200 OK.

Pedí 3 resultados 1
Pedí 9 resultados 1
Pedí 50 resultados 1
Cómo se confirmó

Formulé el diagnóstico como algo que se podía refutar: si el problema es que el índice limita la búsqueda a una lista, entonces pedir más resultados va a seguir devolviendo uno. Pedí 3, 9 y 50. Siempre uno. Hipótesis confirmada de una forma que la habría descartado si fuese falsa.

La solución fue borrar el índice. Con menos de mil filas, el escaneo secuencial es exacto y prácticamente instantáneo. El índice aproximado cambia precisión por velocidad — sobre nueve filas no había velocidad que ganar y sí precisión que perder.

Lo que me llevé

Ese proyecto tuvo seis fallas reales y cinco de las seis devolvían 200 OK. En sistemas con modelos de lenguaje, «responde» y «funciona» son propiedades independientes: un servicio tradicional roto tira un 500, uno con LLM devuelve un párrafo bien redactado que suena razonable.

Los dos errores más caros fueron de exceso de prolijidad, no de descuido: el índice estaba puesto porque «es lo que se hace», y un catch vacío estaba puesto porque «hay que manejar los errores». Las dos decisiones se veían profesionales y las dos rompían el sistema.

03 — Cómo trabajo

Tres cosas que hago siempre

01

Entiendo el proceso manual antes de automatizarlo

Una automatización resuelve poco si no sé exactamente qué problema real estoy sacando del medio. Primero miro cómo se hace hoy, con quién y por qué.

02

Escribo tests para lo que hago

En AMICANA eso significó pasar de «funciona en mi máquina» a una suite de regresión real que corre en cada cambio. No es burocracia: es lo que me deja tocar el código sin miedo.

03

Ningún error se traga en silencio

Degradar con elegancia y ocultar el error son cosas distintas. Si una falla es tolerable, la registro. Si no lo es, la propago. Lo que nunca hago es tragármela.
